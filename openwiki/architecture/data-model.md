# Core data model (@bosco/db)

`packages/db` (`@bosco/db`) holds the Drizzle schema of the `core` Postgres
schema, the SQL migrations generated by drizzle-kit, the migrator and the
demo seed. It is not wired into the API yet. The user-facing guide is
`docs/database.en.md` / `docs/database.fr.md`.

## Tables

| Table | Holds | Rules enforced by the database |
| --- | --- | --- |
| `organisation` | the single organisation of the install | boolean primary key that can only be `true` (`organisation_single_row`), so at most one row |
| `person` | display name, email | email unique ignoring case (`person_email_lower_unique` on `lower(email)`); no link to any login account |
| `team` | name | none beyond the key |
| `team_membership` | person in team, `[started_at, ended_at)` | end after start; no two overlapping periods for the same person in the same team |
| `manager_attachment` | person → manager, `[started_at, ended_at)` | nobody is their own manager; end after start; no two overlapping periods for the same person |

An open period has `ended_at` null. Every foreign key is `ON DELETE
RESTRICT`: a person or team still referenced cannot be deleted.

The overlap rules are `EXCLUDE USING gist` constraints on
`tstzrange(started_at, ended_at)` with the trusted `btree_gist` extension.
drizzle-kit cannot express them, so they live in the hand-written migration
`0001_period_overlap.sql`.

## Migrations and seed

- `pnpm db:migrate` runs the drizzle-orm migrator over
  `packages/db/migrations`; applied migrations are skipped, so it is safe to
  rerun.
- `pnpm db:seed` inserts fictitious demo data (names on `example.com`) with
  fixed ids, so a rerun inserts nothing. It refuses when the database holds a
  non-demo organisation, people or teams.
- New migrations: change `src/schema.ts`, then
  `pnpm --filter @bosco/db db:generate`.
- Local database: root `docker-compose.yml`, service `postgres`
  (`postgres:19`, bound to `127.0.0.1`).

## CSV import

`importPeopleCsv(db, csvText)` (`packages/db/src/people-import.ts`) reads a
header `display_name,email[,manager_email]` with the in-house RFC 4180
parser `packages/db/src/csv.ts`. It validates every line first
(`parsePeopleCsv`) and rejects the whole file with a `PeopleCsvError` that
names lines and columns, never values; a repeated email or a person named
as their own manager is a line error. It then upserts on lowercased email
in one transaction under the advisory lock `bosco.people_import`, and on a
manager change ends the open attachment and opens the next one at the
`clock_timestamp()` read once the lock is held. Emails are ASCII-only, so
JS and Postgres lowercasing agree, unless the database uses a Turkish
locale. One statement per step caps a file at about 20,000 rows (Postgres'
parameter limit). Left out: teams, removing a manager, `;` files, size and
lock-wait limits, manager cycles (rights lot). The
user-facing format is in `docs/database.en.md`.

## Tests

`pnpm test:integration` creates a throwaway database, migrates it twice,
seeds it twice and checks every constraint above rejects bad data. It needs
`DATABASE_URL`; CI runs it in the `integration` job. `pnpm test` needs no
database.

## Product decisions and deferred work

bosco is for managers only: a manager keeps records for people who never log
in, so `person` has no account link. Entering people by hand comes in a later
lot. CSV import exists as a library function only (see above). Manager-cycle prevention is an application rule for the
rights lot; the GDPR deletion cascade is decided with the GDPR lot.
